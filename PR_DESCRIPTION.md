PRODUCT-18391 wants a proper CLI reference (per-resource pages, a full command matrix, a token-scopes table), but hand-writing ~21 resource pages against a CLI with this many verb x resource combinations guarantees drift the moment a flag, scope, or resource gets added. dtctl already exposes its own catalog via `dtctl commands --full -o json`, so this is a feasibility prototype: can the mechanical parts of the docs be generated from that catalog instead of hand-typed, so SMEs only own the prose?

* Adds `scripts/gen-docs/gen_docs.py` + `scripts/gen-docs/gen_all.py` - a stdlib-only, deterministic generator (same input JSON always produces byte-identical output). `gen_docs.py` is the proven core (per-resource pages, `COMMANDS.md`, `TOKEN_SCOPES.md`); `gen_all.py` maps the catalog onto the ~21-file IA from the PRODUCT-18391 plan, including the grouped multi-resource pages.
* Adds `make docs-generate`: builds dtctl, dumps `dtctl commands --full -o json` to a temp file, runs the generator, and writes `docs/resources/*.md`, `docs/COMMANDS.md`, `docs/TOKEN_SCOPES.md`, `docs/INDEX.md` (the resource -> file coverage report). No auth needed (it's a static catalog dump), and it doesn't need dtctl on PATH since it invokes `./bin/dtctl` directly.
* Adds `.github/workflows/docs-generate.yml`, modeled on `lint-docs-templates.yml`'s style: runs `make docs-generate`, then `git diff --exit-code` against the generated paths, so a PR fails if the checked-in docs are stale relative to the binary.
* Actually runs the generator and checks in the output for all 21 planned resource pages, `COMMANDS.md`, `TOKEN_SCOPES.md`, and `INDEX.md`, so this PR is reviewable against real generated content, not just the tooling.

Only the "Overview" and "Examples" sections of each `docs/resources/*.md` page are meant to be hand-authored by SMEs (marked `<!-- SME: ... -->`); everything else - supported operations, flags, required token scopes - is generated and gets clobbered the next time `make docs-generate` runs, so don't hand-edit those sections.

`docs/TOKEN_SCOPES.md` is hand-authored, and this PR keeps it that way: `docs/TOKEN_SCOPES.md` already exists as a 464-line authored doc (quick-reference table, use-case guidance, the client-side-enforcement notes) linked from `WINDOWS.md`, `OAUTH_IMPLEMENTATION.md`, `QUICK_START.md`, and the dev docs. Rather than overwrite it, the generator INJECTS the generated scope tables into a marked block (`<!-- GENERATED:token-scopes:start/end -->`) and leaves all the authored prose intact. The injector refuses to write if those markers are absent, so a hand-authored file can never be silently clobbered. This is the generate-the-data-author-the-prose pattern --- the drift-prone per-resource scope table is generated (fixing the real `trash-documents` vs `trash.documents` drift the old site had), the caveats and guidance stay authored. `docs/COMMANDS.md` is new, no existing collision there.
